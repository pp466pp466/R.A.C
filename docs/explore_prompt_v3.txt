## 二、功能需求（使用者原文整理）

- 建立客服智能機器人系統，採用會員制，提供聊天介面。
- 聊天介面具有 Sidebar，可開關。
- 後端採用 Gemini API Key 呼叫模型。
- 先以 NLP 解析使用者語句，回應具有 JSON 文件格式的 Intent 與 Entity 內容。
- 聊天內容需要被記住。
- 專案需可部署為對外網址，供多人同時使用。
- 本次功能範圍是否包含 RPG 模組，須先於第四節第 0 題決定。

## 三、必須遵守的既有規範

以 AGENTS.md 為準，重點包括：

- 前端離線，禁止 CDN，Vue 3 全域變數模式，禁止 .vue 與 Vite。
- Modal、Toast 與側邊欄（名稱待第 8 題確認）的顯示狀態由 Vue 3 的 v-if / v-show 接管，禁止 Bootstrap JS 與 data-bs-* 互動屬性（唯一例外為 data-bs-theme="dark"）。
- 業務與 Repository 層禁止 Raw SQL，ORM 為唯一操作方式。
- 客服 NLP 解析必須以非串流請求強制輸出標準 JSON，嚴禁將 JSON 原文串流至前端。
- 模型統一為 gemini-3.8-flash。
- 所有客服回應須為繁體中文（zh-TW）。
- 檔案編碼規則依 AGENTS.md 的編碼章節。
- 聊天訊息為 append-only，前端為每則訊息產生唯一 ID，後端以此去重；可變的世界狀態須帶 version。
- 正式環境不得使用 Flask 開發伺服器（整個部署適用）。
- Gemini API Key 只能由後端從環境變數讀取，嚴禁寫入程式碼、模板或版本庫。
- 以下條文僅適用於 RPG 串流功能：
  - 前端串流必須設定逾時，並以 AbortController 中止請求；無論成功、失敗或中斷，皆須在 finally 中恢復 UI 狀態。
  - RPG 的 SSE 端點須運行於支援長連線並發的正式伺服器配置。
  - SSE 串流須有心跳與斷線偵測：定期送出心跳以維持連線；後端偵測到客戶端斷線時停止生成。

## 五、對外部署（新增）

11. **部署方式**：比較自有 VM、雲端 PaaS 與 Tunnel 三種方案的成本、維運負擔、SSE 串流支援與 HTTPS 設定方式，並建議一種。若第 0 題決定 RPG 不納入，此題的 SSE 支援可列為次要條件。

12. **資料庫選擇**：SQLite（WAL）或 SQL Server（Azure SQL 或自架）在多人同時使用時，並發、鎖定與備份的差異為何？是否需要修改 AGENTS.md 第 4 節？

13. **伺服器架構與串流並發**：SSE 串流是單次回覆期間的連線，回覆生成完即結束，不是永久連線。請以「同時生成數 × 平均生成秒數」估算並發上限，每位使用者的串流上限見第 20 題。請決定：
    - gunicorn 的 worker 型態（例如 gevent、eventlet、gthread 或 ASGI），以及在該型態下 RPG 串流能支撐的並發數。
    - 客服的非串流 API 與 RPG 的 SSE 端點是否分開部署或分開 worker 池，避免長串流影響客服請求。
    - Nginx 反向代理的 `proxy_buffering`、`X-Accel-Buffering` 標頭與 `proxy_read_timeout` 設定。
    - 心跳間隔與斷線偵測方式，包括後端偵測斷線後停止 Gemini 生成的機制。
    - 是否啟用 HTTP/2，以避免 HTTP/1.1 下同網域連線數上限造成多分頁互相阻塞。
    請確認 AGENTS.md 第 9 節的現有條文是否採用，或提出修改。

14. **環境與機密**：開發與正式環境的設定如何分離？正式環境的機密要用平台的 secret 功能還是 Docker secrets 注入？金鑰輪替的流程為何？信箱寄信服務的金鑰（第 18 題）是否一併納入同一套機制？

16. **可攜性（次要）**：是否以 Docker 打包，讓其他機器可以重現部署環境？若與正式部署的需求衝突，以正式部署為準。

## 六、多人使用與安全（新增）

17. **資料隔離**：每位使用者只能讀寫自己的對話、Session 與 memory_logs。每個讀寫 API 都必須檢查擁有者，防止透過修改 ID 存取他人資料（IDOR）。是否需要統一的權限檢查層？

18. **身分驗證流程**：登入方式（Flask session cookie 或 token）、密碼雜湊方式、註冊流程（信箱加密碼）、信箱驗證、忘記密碼流程、Google 登入的 OAuth 設定與同信箱的帳號合併規則、session cookie 的 Secure / HttpOnly / SameSite 設定、CSRF 防護、登入失敗次數限制與帳號鎖定。另請決定信箱驗證與忘記密碼所使用的寄信服務，以及寄信相關的設定要放在哪裡（須與第 9、14 題的機密管理一致）。

19. **角色與權限**：各會員等級的權限差異。是否需要管理員後台，用來停權帳號、查看用量、刪除違規內容？

20. **用量與成本控制**：每位使用者的速率限制、每日 Gemini 次數或 token 上限、全站預算上限、同時生成的串流數上限（每位使用者與全站，供第 13 題的並發估算使用），以及超額時的回覆文案（須為繁體中文）。請先依第 3 題的決策估算每次對話的 token 用量，再據此設定上限。

21. **輸入與內容安全**：客服訊息的長度上限、Prompt Injection 防護（使用者輸入與 System Prompt 的隔離方式）、不當內容的過濾與處理流程。

22. **可觀測性**：錯誤日誌、Gemini 呼叫次數與延遲的監控、告警方式。日誌中不得記錄密碼、完整 API Key 或對話全文，請明確定義哪些欄位可以記錄。

23. **備份與個資**：備份頻率、保存期限與還原演練方式。刪除帳號時，對話與個人資料要刪除到什麼範圍？請依適用的個資法規決定，並說明保留期限的依據。

24. **負載測試**：正式部署前，以多人同時對話（含同時生成數）進行壓力測試，確認 worker、資料庫與 Gemini 配額的上限，並以結果回頭調整第 11 到 13 題的決策。

25. **測試策略**：哪些項目需要自動化測試（JSON 驗證、權限檢查、同步去重、登入流程、串流中斷處理），哪些以人工驗證為主？測試環境與正式環境的資料如何隔離？
