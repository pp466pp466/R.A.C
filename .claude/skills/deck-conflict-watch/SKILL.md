# 2.0 簡報衝突監看（deck-conflict-watch）

`docs/2.0簡報.md`（與 `2.0簡報.pdf`）和六張 4K 圖解是**對外報告用的時間點快照**（簡報頁首標明數字取自 2026-11-18 的程式碼與 git 紀錄）。程式會繼續變，簡報不會自動跟著變。使用者的要求是：**之後每次實作或更新既有程式、檔案，只要與 2.0 簡報有衝突，就通知使用者，由使用者決定怎麼做。**

這份技能規範「怎麼發現、怎麼通知」，不記錄任何一次的結果；各次的衝突與使用者的決定寫在 `HANDOFF.md`。

## 1. 鐵則：只通知，不動手

- 發現衝突時，**不修改** `docs/2.0簡報.md`、`docs/2.0簡報.pdf`、六張 PNG、`docs/diagrams/` 的任何檔案；也不「順手」重新產生圖解或 PDF（重產要用 Chrome、mermaid 與 marked，成本高，且是否值得由使用者判斷）。
- 使用者可能選擇：現在改、併入某一批一起改、先記錄不改、或保留（簡報本來就是某個時點的快照）。**由使用者說了算**，不替使用者選。
- 使用者決定「保留不改」的項目，記在 `HANDOFF.md`；同一項事實沒有再變時不重複通知，事實又變了（例如 0018 → 0019 → 0020）才再通知。
- 範圍只有 2.0 簡報與其六張圖解。`1.0簡報`、`report.md`、`RPG.md` 的決定紀錄、封存的 openspec 都是歷史紀錄，不查。

## 2. 什麼時候檢查

任何一項成立就檢查，不因為「改得很小」而略過：

- 每一批 apply 做完、commit 之前（`openspec-batch-workflow` 第 5 節的收尾）。
- 對展示環境或其他環境執行了部署、遷移、換版、回復、拆除，或環境狀態改變。
- 改了資料表、欄位、migration、端點、頁面路由、維運指令、環境變數、流程、分層、前端模組。
- 修訂 `AGENTS.md`、封存或立案 change、路線圖狀態改變。
- 實作了簡報寫「尚未實作」「規劃中」「待部署」的項目，或做了簡報寫「已完成」但之後被改掉的項目。
- 使用者問「簡報有沒有過時」。

## 3. 怎麼檢查

1. **先寫下這次實際改了什麼**：`git diff --stat`、本批 `tasks.md`、部署指令與結果。不憑記憶。
2. **用下表找出可能受影響的簡報章節與圖**。
3. **用搜尋比對，不整份重讀**：到 `docs/2.0簡報.md` 搜相關字樣（遷移編號如 `0019`、提交短碼或映像標籤、改名的函式或端點、事件名稱、數字、「尚未實作」「規劃中」「待部署」「第一次」）。圖是 PNG，不能搜尋，所以**搜產生它們的 `docs/diagrams/build_diagrams.py` 與 `build_diagrams_system.py`**（圖上的文字都寫在這兩個檔案裡）。
4. **判斷是不是衝突**：簡報現寫的內容，與現況（程式、資料庫、環境、規範）不一致才算。簡報已經如實標明「規劃中」「尚未」而現況仍然如此，不算衝突。
5. 把衝突按第 4 節的格式通知使用者，並寫進 `HANDOFF.md`。

### 對照表：改了什麼 → 看簡報哪裡

| 改了什麼 | 簡報的章節 | 圖解與產生器 |

| 程式規模、資料表與欄位數、migration 數、端點數、頁面數、維運指令數、測試案例數、提交數 | 專案摘要表、「從 1.0 到 2.0」的比較表、品質保證與守門測試 | 無 |

## 4. 怎麼通知

在回覆中（不要只寫進 `HANDOFF.md`）用下面的格式，**逐項**列出「事實被推翻或狀態改變」的衝突：

```
與 2.0 簡報有衝突（N 項，請決定怎麼處理）：
1. 位置：docs/2.0簡報.md 第 N 行（「章節名」）；圖：某圖（產生器第 M 行）
   簡報現寫：……
   現況：……（附證據：指令輸出、提交、檔案路徑）
   原因：這次的哪項改動造成
2. …
選項：現在改（簡報、產生器、重產 PNG 與 PDF）／併入某一批／先記錄不改／保留為時間點快照。
我的建議：……（一句話，附理由；仍由你決定）
```

- **數字漂移合併成一行**：測試案例數、行數、提交數、模組數等「每次都會變」的數字，不逐項列，合併成「數字漂移：簡報寫的是 2026-11-18 的快照，現況為……」一行。**狀態與敘述被推翻**（版本、已部署與否、已實作與否、流程、名稱、規範與程式的差異）一律逐項列。
- 沒有衝突時也要說一句「已對照簡報，沒有衝突」，讓使用者知道有檢查過；不要沉默。
- 無法確定是否衝突的，列為「待確認」並說明為什麼，不自行判定。

## 5. 使用者決定之後

- **決定現在改或併入某批時**：依 `docs/diagrams/README.md` 的「何時重新產生」：先改 `build_diagrams.py` 或 `build_diagrams_system.py` 與 `docs/2.0簡報.md`，重新產生圖解與 PDF；簡報裡的 `crop` 隨圖解版面調整；數字重新量過再寫；執行 `docs/diagrams/build_deck.py --check`、目視檢查 PNG 與 PDF；跑 `tests/test_design_docs.py`；簡報與圖解放在同一個提交，且與程式的提交分開。
- **決定保留不改時**：在 `HANDOFF.md` 記下「簡報第 N 行與現況不同，使用者決定保留」，並標明對應的事實與日期。
- 簡報的產生相依（`mermaid`、`marked`）不進版本庫，裝法見 `docs/diagrams/README.md`。

## 6. 與其他技能的關係

- `design-docs-sync`：處理 `docs/` 的八份設計文件與程式一致；本技能處理**簡報與圖解**。兩者互補，改動同時影響兩邊時都要做。
- `openspec-batch-workflow`：每批收尾時呼叫本技能的檢查（第 5 節）。
- 簡報與圖解的內容若與 `AGENTS.md` 衝突，以 `AGENTS.md` 為準（見 `design-docs-sync` 的規則）；本技能只負責通知，不修改規範。
