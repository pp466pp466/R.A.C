對應 AGENTS.md 第 7、8 節。

## 雙核心業務邏輯 (Dual-Core Business Spec)

### 開放世界 RPG 模組

- 無硬性結局 (Endless Open World)：平台預設與首發劇本廢除傳統死亡死局，採用「無窮盡開放世界 + 狀態轉移框架 (State Transition Framework)」；玩家創作的劇本可選擇自訂結局：結局模式為明確選項（無結局為預設，或自訂結局並附結局說明與選填的壽終年齡），不得只靠文字中的字眼判斷；壽終年齡由 Service 判定，結局說明供模型讀取，模型提議的結局須由 Service 確認該劇本為自訂結局後才生效。到結局時存檔進入「已完結」：歷史仍可閱讀，不得再送出新回合，可用同一劇本開新存檔。
- 動態階段錨點：透過 milestones_json 驅動階段性事件（如 20 歲宗門大測），觸發後由 LLM 動態延伸新目標，玩家離線時對話 Session 自動存檔。Milestone 的觸發由 Service 依玩家年齡或遊戲內年份（依劇本曆法的起始年換算）判斷，不由模型宣告。
- 原始劇本（劇本版本 `script_versions` 的 `milestones_json`）為唯讀。LLM 動態延伸的目標不得寫回原始劇本，應另存於 session 層，完成後歸檔。已發佈的劇本版本不可變，修改一律產生新版本；存檔開局時複製劇本內容，之後劇本的修改、下架或刪除不影響進行中的存檔。主角與錨定事實於開存檔時一併寫入存檔（見「玩家主角」一條）。
- NPC 角色卡：NPC 的特質（表層或隱藏）、弧線階段（surface、cracking、revealed）與錨定事實存放於 sessions.entities_json，每回合進入世界狀態；階段由模型提議、Service 驗證轉移，不由模型直接寫入。個性的玩家層修正存放於 user_persona_overrides（跨存檔共用，只存差異），遊戲中新增的其餘內容（人物、背景、世界觀、地點）一律屬於單一存檔（玩家創作的劇本是另一類內容，見下一條）。全站性格原型庫（persona_prototypes）玩家唯讀，由 AI 擬草案、管理員核可後上架，核可上架的原型不得含可回溯到使用者的資料。角色年齡為錨定事實，模型與玩家都不能直接寫入；成年角色不得被改成未成年，衝突時以劇情轉場處理，不顯示錯誤（見第 10 節被擋的回合）。
- 玩家主角：玩家開存檔時依「劇本角色規格」自創主角，與劇本角色共用同一份欄位、長度與列舉值上限，由 Service 驗證，所有劇本一致，圖片 v1 不實作；主角年齡是劇中角色的年齡，與使用者年齡無關。流程為序章（顯示劇本的背景故事，唯讀）、聯繫、創角：玩家可填選填的自我介紹，請 AI 生成主角角色卡與一個錨定事實；生成只是預覽，不寫入存檔，可重新生成（次數有上限，存放於資料庫的設定表，程式每次使用時現讀而不快取於行程內，以 flask 指令修改並寫入稽核紀錄，初始值由遷移寫入），也可先修改再接受；生成失敗、被審查擋下或玩家不想用時，改為自創。按「開始冒險」才開存檔，主角與錨定事實一併寫入。錨定事實每位主角一個，內容為主角與劇本中某個人物、地點或里程碑的關係，必須指向該存檔的劇本內容中存在的項目，由 Service 驗證；模型只提議，玩家接受或自行撰寫後才由 Service 寫入，不由模型直接寫入；自創時預設也須提供一個（選定項目後自行撰寫一句），玩家可略過，略過時開場僅依背景故事與角色卡；主角與對象之一為未成年時，錨定事實不得為戀愛或性的關係。主角的年齡為錨定事實，開存檔後模型與玩家都不能直接寫入。主角的所有文字（角色卡、自我介紹、錨定事實）須通過與劇本設定相同的審查層：規則層於每次生成與送出時執行，模型層於開存檔時執行，未通過者不得開存檔；拒絕只告知類別。
- 開場：主角建立完成後，由回合引擎依主角角色卡與錨定事實產生「第 0 幕」，沿用串流、審查層與被擋回合的處理（見第 10 節），並受內容分級上限約束；第 0 幕不是一輪（見第 6 節），選定後存於存檔，重新整理或換裝置不重抽；產生失敗或被擋時，退回劇本的初始對話，沒有則只顯示背景故事；它的 token 計入全站每日用量，不計入每日對話輪數。
- 玩家創作劇本：v1 開放玩家依固定規格創作劇本並可公開分享。規格為所有劇本共用的通用核心（目錄資訊、背景與體系、角色、地點、里程碑、結局、初始對話；欄位、長度、數量與列舉值有上限，由 Service 驗證，並設總量上限以控制每回合的上下文成本）；世界特有的系統以自由文字撰寫，不另設類型範本。圖片 v1 不實作，只預留欄位，非空值一律拒絕。劇本屬於作者，公開分享採先審後發：每個送審公開的劇本須經管理員核可才上架，已發佈的版本不可變、修改產生新版本，核可前舊版持續有效。劇本設定的所有文字欄位須通過伺服器端自有的審查層：明確涉及未成年的性內容、性暴力、非自願的性情節或以真人名義的性內容者直接拒絕，不進人工；有疑慮者進人工並標示類別；一般的未成年角色（如親子、育兒、校園日常）不得誤擋；規則層於每次儲存時執行，模型層於開存檔或送出公開且內容有變動時執行，未通過者不得用來開存檔；限制單位時間內的送審次數；同一作者連續被自動拒絕達門檻次數時，暫停其發佈權限（獨立於帳號鎖定的狀態，只停止送審，其餘功能照常；暫停者可使用申訴頁，管理員檢視申訴與解除沿用帳號鎖定的規則：須重新輸入密碼並寫入稽核）；拒絕只告知類別，不指出內容。每位會員的劇本數量與送審次數有上限，依會員等級；這些上限與連續被拒的門檻存放於資料庫的設定表，程式每次使用時現讀而不快取於行程內，以 flask 指令修改並寫入稽核紀錄，初始值由遷移寫入。
- 內容分級：內容程度為三種模式，以單一欄位 content_tier 表示（由保守到寬鬆）：safe（安全模式）、standard（一般模式：浪漫、曖昧與感官，但不露骨，成年玩家的預設）、adult（成人模式：成年角色之間合意的露骨內容）；預設最保守。成人模式須同時滿足三項：已取得所用模型供應商的書面許可與法務意見（許可涵蓋的供應商、模型與日期須記錄，且須涵蓋實際使用的模型）；部署層的環境設定開啟（預設關閉，development 可開啟供個人測試，staging 與 production 須明確設定才生效，不得在程式中寫死為開啟）；玩家已在切換為成人模式時完成成年確認：須勾選「我確定已滿 18 歲」與同意安全規範兩項，且由生日算出的年齡已滿 18 歲，並記錄確認時間、安全規範的版本與確認方式（目前為自行聲明）；不另設證件或第三方驗證，日後若法務意見要求更強的方式，只更換確認方式。玩家在個人頁面以開關決定是否開啟成人模式，預設關閉，未開啟時為一般模式；成年玩家也可自行選擇安全模式。實際生效的模式為玩家設定、劇本宣告與年齡上限三者中最保守者；劇本由作者宣告其 content_tier，安全模式的玩家只能看到與遊玩宣告為安全的劇本，未滿 18 歲的作者只能宣告安全。內容上限由 AccessPolicy 依使用者年齡決定（年齡由生日計算，見第 10 節）：未滿 18 歲者一律為安全模式，不論任何設定都不得提高，介面須顯示提示說明原因；滿 18 歲後該限制自動解除，但玩家的模式與既有存檔的旗標不自動調高，介面提示玩家可自行切換；當玩家輸入曖昧內容而目前模式較保守時，系統只提醒玩家可調整，不得自動調高；存檔旗標只能在上限之內調整。安全模式須嚴格執行，由伺服器端的 system_instruction、安全設定與審查層共同套用，不依賴模型自行判斷使用者的年齡，也不依賴模型拒絕：安全模式不得出現性行為與性暗示（含以隱喻、省略或暗示帶過），不得描寫性器官、脫衣與帶有性意味的撫摸；牽手、擁抱、告白與簡短的親吻等一般的親密情感表達允許；另不得出現露骨的暴力血腥與虐待描寫，以及自殺與自殘方法的描寫；界線不明確時一律以較保守的判定處理。一般模式可有性暗示、深吻與情慾張力，但性行為與性器官只能淡出或暗示，不得描寫，由審查層驗證，不因所用模型不拒絕而放寬。無論模式，一律禁止涉及未成年（含看似未成年的角色）的性內容、性暴力與非自願的性情節，以及以真人名義的性內容；露骨場景中的每個角色須有成年年齡紀錄。上述禁止項須由伺服器端自有的審查層執行，不得僅依賴模型拒絕；使用不具拒絕行為的模型時，此層為必要條件。

### 會員制智能客服機器人模組

- 類 ChatGPT 介面：具備可開關的左側歷史對話 Sidebar (寬度 280px) 與會員等級標籤；響應式行為與建議動作 chips 見 [frontend.md](frontend.md)。
- 會員制：以 email 為帳號識別，一組 email 只能對應一個帳號。會員等級為 free（一般）、plus（進階）、vip（尊榮），僅影響額度、不影響權限；初始額度為每日對話輪數 30 / 100 / 300、每分鐘訊息數 6 / 10 / 20、對話數上限 20 / 100 / 500，單則訊息上限皆為 1000 字；RPG 記事簿容量 2000 / 5000 / 10000 字（見第 6 節）。
- NLP 意圖與實體解析：Service 層呼叫 Gemini API 時強制要求以非串流請求輸出標準 JSON（至少包含 intent, confidence, entities, reply_text, suggested_actions）（見 [llm-streaming.md](llm-streaming.md)）。
- 客服僅由 AI 提供，不設真人客服通道。使用者要求真人客服時，AI 須以繁體中文說明並引導以意見回饋留下紀錄，供管理員於後台檢視。
- 知識範圍：v1 僅回答平台自身資訊（登入與帳號、會員等級與額度、意見回饋流程）；超出範圍或沒有資料來源的問題歸為 unknown，並引導以意見回饋留下紀錄。有 FAQ 文件時再另行擴充，不採檢索式 (RAG)。

## 語系與字元編碼規範（繁體中文與 UTF-8 強約束）

### 全系統語言統一（Traditional Chinese）

- 所有 UI 介面文字、系統 Prompt、錯誤訊息、註解、選單、Modal/Toast 提示、預設劇本內容與客服回應，一律強制採用繁體中文（zh-TW，台灣常用術語）；唯一例外是必須純 ASCII 的檔案（見下方檔案編碼規範）。
- 要求 Gemini API 生成內容時，必須在 System Prompt 中明確約束回傳繁體中文。
- 系統寄出的信件（營運告警與管理員的重設密碼信）一律為 UTF-8 編碼與繁體中文內容。

### 檔案編碼與 I/O 規範

- 後端檔案讀寫：Python 處理文字、JSON、CSV、檔案讀寫（open()）或匯出/匯入操作時，必須明確指定 encoding，嚴禁使用 ANSI 或未指定之編碼。
  - 讀取：一律使用 encoding='utf-8-sig'（可自動去除 BOM）。
  - 寫入 JSON 與一般文字檔：使用 encoding='utf-8'，避免 BOM 導致 JavaScript 的 JSON.parse 解析失敗。
  - 匯出供 Windows/Excel 開啟的 CSV：使用 encoding='utf-8-sig'，確保繁體中文絕不亂碼。
- 資料庫與 HTML 標籤：SQLAlchemy 連線與文字欄位必須支援 Unicode（見 [database.md](database.md)）；HTML 模板標註 <meta charset="UTF-8"> 與 <html lang="zh-Hant-TW">。
- 以系統地區編碼讀取的檔案與腳本：
  - alembic.ini 與 script.py.mako 必須純 ASCII（見 [database.md](database.md)）。
  - Windows PowerShell 5.1 以系統編碼讀取沒有 BOM 的 .ps1；內含繁體中文或其他非 ASCII 字元的 .ps1 須存成 UTF-8 with BOM，否則會亂碼。
  - 需要輸出繁體中文訊息，或要把字串傳給外部程式（例如 wsl、docker）的維運與驗收腳本，一律以 Python 撰寫（UTF-8、參數以清單傳遞）；.ps1 只作為純 ASCII 的薄包裝（例如容器驗收的 scripts/verify_container.py 與 scripts/verify-container.ps1）。
