## 雙核心業務邏輯 (Dual-Core Business Spec)

### 開放世界 RPG 模組

- 無硬性結局 (Endless Open World)：平台預設與首發劇本廢除傳統死亡死局，採用「無窮盡開放世界 + 狀態轉移框架 (State Transition Framework)」；玩家創作的劇本可選擇自訂結局：結局模式為明確選項（無結局為預設，或自訂結局並附結局說明與選填的壽終年齡），不得只靠文字中的字眼判斷；壽終年齡由 Service 判定，結局說明供模型讀取，模型提議的結局須由 Service 確認該劇本為自訂結局後才生效。到結局時存檔進入「已完結」：歷史仍可閱讀，不得再送出新回合，可用同一劇本開新存檔。
- 動態階段錨點：透過 milestones_json 驅動階段性事件（如 20 歲宗門大測），觸發後由 LLM 動態延伸新目標，玩家離線時對話 Session 自動存檔。Milestone 的觸發由 Service 依玩家年齡或遊戲內年份（依劇本曆法的起始年換算）判斷，不由模型宣告。
- 原始劇本（劇本版本 `script_versions` 的 `milestones_json`）為唯讀。LLM 動態延伸的目標不得寫回原始劇本，應另存於 session 層，完成後歸檔。已發佈的劇本版本不可變，修改一律產生新版本；存檔開局時複製劇本內容，之後劇本的修改、下架或刪除不影響進行中的存檔。主角與錨定事實於開存檔時一併寫入存檔（見「玩家主角」一條）。
- NPC 角色卡：NPC 的特質（表層或隱藏）、弧線階段（surface、cracking、revealed）與錨定事實存放於 sessions.entities_json，每回合進入世界狀態；階段由模型提議、Service 驗證轉移，不由模型直接寫入。個性的玩家層修正存放於 user_persona_overrides（跨存檔共用，只存差異），遊戲中新增的其餘內容（人物、背景、世界觀、地點）一律屬於單一存檔（玩家創作的劇本是另一類內容，見下一條）。全站性格原型庫（persona_prototypes）玩家唯讀，由 AI 擬草案、管理員核可後上架，核可上架的原型不得含可回溯到使用者的資料。角色年齡由模型提議，Service 驗證格式與合理範圍後寫入，可往任何方向更正，每次更正須通知玩家並附更正前的年齡；年齡紀錄未滿 18 歲的角色，或文字明確寫出未成年的年齡或身分且與性內容同段或相鄰句者，一律不得有性內容，不論模式，由審查層擋下並依第 10 節被擋的回合處理；模糊的外貌描述與年齡未知不單獨構成阻擋。年齡只有劇本內設的重要角色與玩家主角一定有；玩家對話中產生的其餘角色不需要有明確年齡，除非對話中特別標示，沒有明確年齡的角色在露骨場景也不因此被擋（只擋明確未成年者）。
- 玩家主角：玩家開存檔時依「劇本角色規格」自創主角，與劇本角色共用同一份欄位、長度與列舉值上限（主角另有「來歷」欄位：本地人或穿越者，劇本角色沒有），由 Service 驗證，所有劇本一致，圖片 v1 不實作；主角年齡是劇中角色的年齡，與使用者年齡無關。流程為序章（顯示劇本的背景故事，唯讀）、聯繫、創角：玩家可填選填的自我介紹，請 AI 生成主角角色卡與一個錨定事實；生成只是預覽，不寫入存檔，可重新生成（次數有上限，存放於資料庫的設定表，程式每次使用時現讀而不快取於行程內，以 flask 指令修改並寫入稽核紀錄，初始值由遷移寫入），也可先修改再接受；生成失敗、被審查擋下或玩家不想用時，改為自創。按「開始冒險」才開存檔，主角與錨定事實一併寫入。錨定事實每位主角一個，內容為主角與劇本中某個人物、地點或里程碑的關係，必須指向該存檔的劇本內容中存在的項目，由 Service 驗證；模型只提議，玩家接受或自行撰寫後才由 Service 寫入，不由模型直接寫入；自創時預設也須提供一個（選定項目後自行撰寫一句），玩家可略過，略過時開場僅依背景故事與角色卡；錨定事實不得為性的關係，也不得為性奴等禁斷關係；戀愛、婚姻與婚約類的關係不論年齡一律開放（例如青梅竹馬，須用符合劇本世界觀的說法，仍不得涉及性）。主角的年齡於開存檔時寫入，之後依 NPC 年齡的相同規則更正（見 NPC 角色卡一條）。主角的所有文字（角色卡、自我介紹、錨定事實）須通過與劇本設定相同的審查層：規則層於每次生成與送出時執行，模型層於開存檔時執行，未通過者不得開存檔；拒絕只告知類別。來歷為穿越者時，由固定的 system_instruction 加入平台規則（保留現代知識與格格不入的反差），規則文字不來自玩家；既有存檔缺值視為本地人；AI 生成的預覽不決定來歷，由玩家選擇。
- 開場：主角建立完成後，由回合引擎依主角角色卡與錨定事實產生「第 0 幕」，沿用串流、審查層與被擋回合的處理（見第 10 節），並受內容分級上限約束；第 0 幕不是一輪（見第 6 節），選定後存於存檔，重新整理或換裝置不重抽；產生失敗或被擋時，退回劇本的初始對話，沒有則只顯示背景故事；它的 token 計入全站每日用量，不計入每日對話輪數，也不消耗遊戲幣。
- 玩家創作劇本：v1 開放玩家依固定規格創作劇本並可公開分享。規格為所有劇本共用的通用核心（目錄資訊（含讀者頻道）、背景與體系、角色、地點、里程碑、結局、初始對話；欄位、長度、數量與列舉值有上限，由 Service 驗證，並設總量上限以控制每回合的上下文成本）；世界特有的系統以自由文字撰寫，不另設類型範本。圖片 v1 不實作，只預留欄位，非空值一律拒絕。劇本屬於作者，公開分享採先審後發：每個送審公開的劇本須經管理員核可才上架，已發佈的版本不可變、修改產生新版本，核可前舊版持續有效。讀者頻道（audience）為單選：男頻、女頻、全讀者；既有劇本視為全讀者；屬版本內容，修改須產生新版本並重新送審。劇本設定的所有文字欄位須通過伺服器端自有的審查層：明確涉及未成年的性內容、性暴力、非自願的性情節或以真人名義的性內容者直接拒絕，不進人工；有疑慮者進人工並標示類別；一般的未成年角色（如親子、育兒、校園日常）不得誤擋；規則層於每次儲存時執行，模型層於開存檔或送出公開且內容有變動時執行，未通過者不得用來開存檔；限制單位時間內的送審次數；同一作者連續被自動拒絕達門檻次數時，暫停其發佈權限（獨立於帳號鎖定的狀態，只停止送審，其餘功能照常；暫停者可使用申訴頁，管理員檢視申訴與解除沿用帳號鎖定的規則：須重新輸入密碼並寫入稽核）；拒絕只告知類別，不指出內容。每位會員的劇本數量與送審次數有上限，依會員等級；這些上限與連續被拒的門檻存放於資料庫的設定表，程式每次使用時現讀而不快取於行程內，以 flask 指令修改並寫入稽核紀錄，初始值由遷移寫入。
- 內容分級：內容程度為三種模式，以單一欄位 content_tier 表示（由保守到寬鬆）：safe（安全模式）、standard（一般模式：浪漫、曖昧與感官，但不露骨，成年玩家的預設）、adult（成人模式：成年角色之間合意的露骨內容）；預設最保守。成人模式須同時滿足三項：已取得所用模型供應商的書面許可與法務意見（許可涵蓋的供應商、模型與日期須記錄，且須涵蓋實際使用的模型）；部署層的環境設定開啟（預設關閉，development 可開啟供個人測試，staging 與 production 須明確設定才生效，不得在程式中寫死為開啟）；玩家已在切換為成人模式時完成成年確認：須勾選「我確定已滿 18 歲」與同意安全規範兩項，且由生日算出的年齡已滿 18 歲，並記錄確認時間、安全規範的版本與確認方式（目前為自行聲明）；不另設證件或第三方驗證，日後若法務意見要求更強的方式，只更換確認方式。玩家在個人頁面以開關決定是否開啟成人模式，預設關閉，未開啟時為一般模式；成年玩家也可自行選擇安全模式。實際生效的模式為玩家設定、劇本宣告與年齡上限三者中最保守者；劇本由作者宣告其 content_tier，安全模式的玩家只能看到與遊玩宣告為安全的劇本，未滿 18 歲的作者只能宣告安全。內容上限由 AccessPolicy 依使用者年齡決定（年齡由生日計算，見第 10 節）：未滿 18 歲者一律為安全模式，不論任何設定都不得提高，介面須顯示提示說明原因；滿 18 歲後該限制自動解除，但玩家的模式與既有存檔的旗標不自動調高，介面提示玩家可自行切換；當玩家輸入曖昧內容而目前模式較保守時，系統只提醒玩家可調整，不得自動調高；存檔旗標只能在上限之內調整。安全模式須嚴格執行，由伺服器端的 system_instruction、安全設定與審查層共同套用，不依賴模型自行判斷使用者的年齡，也不依賴模型拒絕：安全模式不得出現性行為與性暗示（含以隱喻、省略或暗示帶過），不得描寫性器官、脫衣與帶有性意味的撫摸；牽手、擁抱、告白與簡短的親吻等一般的親密情感表達允許；另不得出現露骨的暴力血腥與虐待描寫，以及自殺與自殘方法的描寫；界線不明確時一律以較保守的判定處理。一般模式可有性暗示、深吻與情慾張力，但性行為與性器官只能淡出或暗示，不得描寫，由審查層驗證，不因所用模型不拒絕而放寬。無論模式，一律禁止涉及未成年（含看似未成年的角色）的性內容、性暴力與非自願的性情節，以及以真人名義的性內容；判定依年齡紀錄與文字的明確線索（年齡紀錄未滿 18 歲，或文字明確寫出未成年的年齡或身分），沒有明確年齡的角色不因此被擋，露骨場景也一樣。上述禁止項須由伺服器端自有的審查層執行，不得僅依賴模型拒絕；使用不具拒絕行為的模型時，此層為必要條件。劇情輸出在送達玩家之前，須由伺服器端自有的審查層逐句檢查（以保留一句緩衝的方式串流，通過才釋放）：明確違規與依目前模式界線不明確者一律擋下（取保守），單獨出現的暴力或犯罪用語不擋但記錄類別；不另設每回合的模型層審查（模型層用於劇本與主角；記事簿條目只用規則層）；跨句的未成年判定須納入在場角色的年齡紀錄。
- 遊戲幣（RPG）：RPG 劇情對話一律消耗遊戲幣；會員制智能客服不消耗，仍使用每日對話輪數、每分鐘訊息數與對話數上限，RPG 不使用這兩項額度。一輪（一則玩家訊息加一則完整的 AI 回應，含該輪的狀態呼叫與記事簿抓取）消耗 30 幣；第 0 幕不消耗；沒有成功生成（失敗、中斷、被擋）時不扣，其後同一則訊息的重送與被擋回合的自動重生不再次扣。取得方式：首次註冊登入送 200 免費幣（於年齡確認通過時發放）；每日簽到每次 200 免費幣，台灣時間 0 點刷新；之後僅能透過簽到、儲值與訂閱取得（儲值與訂閱的規範待金流探索後另訂）。免費幣上限 1000，只限制新發放（簽到、贈幣）：領取會超過上限時須先提醒，由玩家選擇取消（不消耗當日簽到）或領取（超出部分作廢）；退款與管理員調整不受上限限制。幣不過期（免費、付費相同）；扣款先扣免費幣、再扣付費幣。扣款於回合開始時原子預扣、完成時結算、失敗時原路退回，以存檔、client_msg_id 與版本為冪等鍵，不得出現負餘額；卡在生成中逾時的預扣由系統退回；餘額不足回 409 與代碼 insufficient_coins。消耗不因會員等級而異。30、200、簽到金額與上限為初始值，存放於資料庫的設定表，程式每次使用時現讀而不快取於行程內，以 flask 指令修改並寫入稽核紀錄，初始值由遷移寫入。
- 玩家重新生成與編輯輸入（RPG）：玩家只能對「最後一輪」重新生成其 AI 回應，或編輯該輪的玩家輸入後重送；AI 的輸出玩家不能直接修改；下一輪開始後即不可再動。重新生成：每個回合前 2 次免費，第 3 次起每次消耗 30 幣；按下時須跳出對話框，玩家必須選擇分類並填寫理由（5 至 50 字，只需重點）才能送出。編輯輸入：消耗 30 幣（原本那輪已扣的幣不退），並使該回合的免費重新生成次數歸零；按下前須提醒會再次消耗遊戲幣並顯示餘額，餘額不足時不得送出。新回應須完整通過審查與狀態驗證才原子替換舊回應；失敗、中斷或被擋時保留舊內容、退回預扣、不消耗免費次數；被取代的輸入與輸出不保存。並行操作以回合的 revision 偵測，不一致時以後端為準。理由只供營運檢視，不得送入模型、不得進入 system_instruction。
- 故事偏好：玩家可選男頻、女頻、全讀者，預設全讀者，只影響劇本目錄的排序（符合偏好者排最前，其次全讀者，其餘仍可瀏覽）；不影響內容分級、敘事與權限。
- 對話人設：玩家可保存可重用的主角角色卡模板（不含錨定事實，錨定事實綁特定劇本），開存檔時預填並複製進存檔，之後修改人設不影響既有存檔；每位玩家可標記一個預設人設（開存檔時預填，非強制）。數量上限依會員等級，初始值 free 3、plus 5、vip 10，存放於資料庫的設定表，程式每次使用時現讀，以 flask 指令修改並寫入稽核紀錄。人設文字視為使用者文字，須通過與主角相同的審查層，隨帳號刪除並納入個人資料匯出。

### 會員制智能客服機器人模組

- 類 ChatGPT 介面：具備可開關的左側歷史對話 Sidebar (寬度 280px) 與會員等級標籤；響應式行為與建議動作 chips 見 [frontend.md](frontend.md)。
- 會員制：以 email 為帳號識別，一組 email 只能對應一個帳號。會員等級為 free（一般）、plus（進階）、vip（尊榮），僅影響額度、不影響權限；初始額度為每日對話輪數 30 / 100 / 300、每分鐘訊息數 6 / 10 / 20、對話數上限 20 / 100 / 500，單則訊息上限皆為 1000 字；RPG 記事簿容量 2000 / 5000 / 10000 字（見第 6 節）；RPG 劇情對話不使用每日對話輪數與每分鐘訊息數，改以遊戲幣控制（見「遊戲幣（RPG）」一條）。
- NLP 意圖與實體解析：Service 層呼叫 Gemini API 時強制要求以非串流請求輸出標準 JSON（至少包含 intent, confidence, entities, reply_text, suggested_actions）（見 [llm-streaming.md](llm-streaming.md)）。
- 客服僅由 AI 提供，不設真人客服通道。使用者要求真人客服時，AI 須以繁體中文說明並引導以意見回饋留下紀錄，供管理員於後台檢視。
- 知識範圍：v1 僅回答平台自身資訊（登入與帳號、會員等級與額度、意見回饋流程）；超出範圍或沒有資料來源的問題歸為 unknown，並引導以意見回饋留下紀錄。有 FAQ 文件時再另行擴充，不採檢索式 (RAG)。

## 語系與字元編碼規範（繁體中文與 UTF-8 強約束）

### 全系統語言統一（Traditional Chinese）

- 所有 UI 介面文字、系統 Prompt、錯誤訊息、註解、選單、Modal/Toast 提示、預設劇本內容與客服回應，一律強制採用繁體中文（zh-TW，台灣常用術語）；唯一例外是必須純 ASCII 的檔案（見下方檔案編碼規範）。
- 要求 Gemini API 生成內容時，必須在 System Prompt 中明確約束回傳繁體中文。
- 系統寄出的信件（營運告警與管理員的重設密碼信）一律為 UTF-8 編碼與繁體中文內容。

### 檔案編碼與 I/O 規範

- 後端檔案讀寫：Python 處理文字、JSON、CSV、檔案讀寫（open()）或匯出/匯入操作時，必須明確指定 encoding，嚴禁使用 ANSI 或未指定之編碼。
  - 讀取：一律使用 encoding='utf-8-sig'（可自動去除 BOM）。
  - 寫入 JSON 與一般文字檔：使用 encoding='utf-8'，避免 BOM 導致 JavaScript 的 JSON.parse 解析失敗。
  - 匯出供 Windows/Excel 開啟的 CSV：使用 encoding='utf-8-sig'，確保繁體中文絕不亂碼。
- 資料庫與 HTML 標籤：SQLAlchemy 連線與文字欄位必須支援 Unicode（見 [database.md](database.md)）；HTML 模板標註 <meta charset="UTF-8"> 與 <html lang="zh-Hant-TW">。
- 以系統地區編碼讀取的檔案與腳本：
  - alembic.ini 與 script.py.mako 必須純 ASCII（見 [database.md](database.md)）。
  - Windows PowerShell 5.1 以系統編碼讀取沒有 BOM 的 .ps1；內含繁體中文或其他非 ASCII 字元的 .ps1 須存成 UTF-8 with BOM，否則會亂碼。
  - 需要輸出繁體中文訊息，或要把字串傳給外部程式（例如 wsl、docker）的維運與驗收腳本，一律以 Python 撰寫（UTF-8、參數以清單傳遞）；.ps1 只作為純 ASCII 的薄包裝（例如容器驗收的 scripts/verify_container.py 與 scripts/verify-container.ps1）。
