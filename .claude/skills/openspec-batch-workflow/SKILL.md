# OpenSpec 分批開發流程（openspec-batch-workflow）

一個 change 的任務通常橫跨資料層、Service、API、前端與文件，一次做完會讓 context 過長、失敗時難以定位。這份技能規範如何把 change 切成批次、何時換對話、測試怎麼跑，以及每批結束時交接與 commit 的做法。它與 `openspec-*` 技能搭配使用，不取代它們；進度與狀態不寫在這裡，寫在 `tasks.md` 與 `HANDOFF.md`。

## 1. 流程總覽

| 階段 | 做什麼 | 產出寫進哪裡 |
|---|---|---|
| explore（`/openspec-explore`） | 釐清問題、比較方案，不寫程式。一次只問一個問題並附建議 | 結論與已確認的決定寫進 `docs/RPG.md`、`docs/report.md`（決策紀錄含備選方案與理由）；尚未立案的項目與順序寫進 `docs/路線圖-roadmap.md`。規範需要修訂時，草案給使用者審，核可後才改 `AGENTS.md` |
| propose（`/openspec-propose`） | 把 change 的範圍、設計與任務寫成可驗證的文件 | `openspec/changes/<名稱>/` 的 `proposal.md`、`design.md`、`specs/<能力>/spec.md`（delta）、`tasks.md`；以 `openspec validate <名稱> --strict` 驗證 |
| apply（`/openspec-apply-change`） | 依 `tasks.md` 實作、測試、同步文件；每完成一項就勾選 | 程式與測試；`tasks.md` 的勾選；`README.md`（端點表、指令、驗收紀錄）；`docs/` 設計文件（`design-docs-sync` 技能）；動到 SQL Server `project` 時同步 `docs/project資料結構文件.md` |
| archive（`/openspec-archive-change`） | 使用者驗收後，把 delta 同步到主規格並封存 | `openspec/specs/` 的主規格；`openspec/changes/archive/<日期>-<名稱>/`；`docs/路線圖-roadmap.md` 的狀態與日期 |

順序固定，不跳關：沒有 propose 就不 apply，沒有使用者驗收就不 archive。規範（`AGENTS.md`）的修訂先單獨 commit，再立案；實作、測試與文件一起 commit。

## 2. 分批原則

apply 之前，先讀 `tasks.md`，**把任務分組並請使用者確認後才開始實作**：

1. **同一架構的任務一起做**：同一層、同一組檔案、同一種測試的任務放同一批（例如資料表與 Repository、Service 與其單元測試、Controller 與 API 測試、前端模組、文件）。分組依據是「改動的檔案與驗證方式是否相同」，不是任務編號的順序。
2. **先分析、確認後再執行**：列出每一批包含哪些任務、為什麼這樣分、批與批之間的依賴與建議順序、每批的驗證方式，交給使用者確認或調整；未經確認不開始第一批。
3. **不確定歸屬的任務要標出來，不自行歸類**：任務跨層、描述含糊、或依賴尚未決定的事項時，在分組結果中獨立列為「待確認」，說明可能歸屬哪幾批與各自的影響，由使用者決定。
4. **一批只做一批**：每批的範圍以使用者確認的分組為準；執行中發現需要超出範圍的改動，先說明並請使用者決定，不順手擴大。
5. **範圍之外的發現照實記下**：發現與本批無關的問題（既有的測試失敗、文件不一致、規範衝突）時，記進 `HANDOFF.md` 的未解決問題，不在本批順手修，除非它阻擋本批。

## 3. 換對話時機

**適合換**（換之前先完成第 5 節的交接）：

- **階段邊界**：explore 結束、propose 完成、apply 的一批 commit 之後、archive 完成之後。
- **context 偏高**：對話已很長，或接下來要讀大量檔案時，趁著一個穩定的停點換。
- **下一步不需要剛才的脈絡**：下一批與前一批用到的檔案、決定幾乎不重疊時，換對話比帶著舊脈絡便宜也更不容易混淆。

**不換**：

- **正在改檔案**：有寫到一半的修改、尚未存檔或尚未通過驗證的編輯。
- **正在除錯**：失敗原因還沒釐清，現場資訊（錯誤訊息、已排除的假設）都在目前的對話裡。
- 工作樹裡有只存在於這個對話的暫時狀態（背景行程、暫時環境）尚未收尾時。

換對話前，工作樹要在一個說得清楚的狀態：要麼已 commit，要麼在 `HANDOFF.md` 寫明哪些檔案是未完成的、為什麼。

## 4. 測試規則

- **任務有依賴時，逐個跑相關測試**：後面的任務建立在前面的結果上（例如 Repository → Service → API），每完成一個任務就跑它直接相關的測試檔，通過再往下，避免錯誤沿著依賴往上累積。
- **任務彼此獨立時，全部完成後跑一次**：不互相依賴的任務可以連續做完，再一次跑涵蓋它們的測試。
- **測試輸出只回報摘要**：通過與失敗的筆數、失敗的測試名稱與一行原因；用安靜模式（`-q`）執行，不貼完整輸出。**失敗時才去看細節**，只展開失敗的那幾項。
- **全套測試在收尾時跑**：一批的相關測試通過即可繼續；整個 change 要交付驗收或封存之前，跑一次全套（pytest 與 Node 測試），並把筆數寫進驗收紀錄。
- **不要宣稱沒有執行過的結果**：沒跑的測試、沒驗證的環境，照實列為「未驗證」。
- **專案慣例**：使用 `.venv` 的 Python（`.venv\Scripts\python.exe -m pytest`）；連真實 SQL Server `project_test` 的測試同時只能有一個 pytest 行程；測試不得指向 `project`。
- 修改測試的斷言去配合新行為時，要確認是行為「刻意改變」造成的，不是掩蓋缺陷。

## 5. 交接與 commit

**每個階段結束都更新 `HANDOFF.md`**（使用者要求）：explore、propose、apply（每一批）、archive 各自做完都要更新，不是只在 apply 的批次結束時。explore 與 propose 結束時至少寫明：目前階段、已確認的決定（指向記錄的位置）、下一步、待使用者核可的事項。`HANDOFF.md` 不進 commit。

每一批做完（或需要換對話時）：

1. **更新 `HANDOFF.md`**（專案根目錄，不進版本庫的交接文件），至少包含：
   - **已完成的範圍**：這一批完成了哪些任務、驗證結果（測試筆數與未驗證項目）。
   - **下一步**：下一批是哪些任務、建議的起點與需要先確認的事。
   - **未解決的問題**：待使用者決定的事項、已知的限制、順手發現但沒處理的問題。
   - 內容只寫事實與路徑，不貼機密、不貼個資。
2. **確認 `tasks.md` 的勾選與實際一致**，且相關文件（README、設計文件）已隨程式更新。
3. **commit**：
   - 使用者要求提交才提交；先看 `git status`，只加入屬於這一批的檔案，不使用 `git add -A` 夾帶無關的變動。
   - commit 訊息用繁體中文，說明這一批做了什麼與驗證結果；結尾附上專案要求的共同作者行。
   - 規範（`AGENTS.md`）的修訂、技能或文件的獨立修改，各自單獨 commit。
4. **commit 之後停止**：向使用者回報這一批的結果與下一步建議，**不自行開始下一批**。下一批由使用者確認後（通常在新的對話）再開始。

## 6. 讀檔規則

- **只讀任務需要的檔案**：先用搜尋找到相關位置，再只讀需要的區段；大檔案用範圍讀取，不整份讀進來。
- **已 commit 的任務不重新檢查**：前面的批次已經 commit 並驗證過的程式與測試，除非本批的任務直接修改或依賴它，否則不重讀、不重跑、不重新審視；信任 `tasks.md`、`HANDOFF.md` 與 git 歷史記錄的結論。
- **接手時的最小閱讀**：新對話開始先讀 `HANDOFF.md`、`git status`、`git log` 與本批相關的 `tasks.md` 區段；其餘按需要再讀。
- **不重做已完成的部分**：發現某項看起來已經做過時，先查 `tasks.md` 與 git 歷史，確認後直接往下，不為了「保險」重寫。
- 讀到機密（`.env` 等）時不在對話中複述其內容。
