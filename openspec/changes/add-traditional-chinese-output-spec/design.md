# Design

## Context

簡轉繁已經在 `app/services/zh_text.py` 實作，套用在劇情串流的審查狀態機（回合、第 0 幕、重新生成與編輯共用同一個基底）與三種結構化輸出（狀態呼叫、記事簿重點抓取、主角生成）；客服（Gemini）與審查類輸出不經過。「杰」的保留是 `safe-mode-toggle` 驗收時加的（`_KEPT_VARIANTS`）。實作與測試（`tests/test_zh_text.py`，54 項）都在，設計文件有說明（`docs/模型呼叫層-llm-layer.md` 第 12 節），唯獨主規格沒有。動機見 proposal.md。這個 change 只寫規格，不碰程式。

## Goals / Non-Goals

**Goals:**
- 把既有行為寫成可驗證的規格：每個情境都能對到現有的測試，沒有測試的情境在 tasks 補上。
- 讓「保留的異體字」有一個明確的修改入口：日後要增加（或移除）要保留的字，就是這份規格的一個 MODIFIED 需求，不是悄悄改程式。

**Non-Goals:**
- 不新增、不改變任何行為（程式與資料都不動）。
- 不處理英文夾雜的偵測或翻譯（規格只寫「伺服器端不翻譯」這個事實）。
- 不涵蓋客服的繁體中文保證（那是 Gemini 的系統指令與其結構化輸出，另一條路徑）。
- 不回溯改寫已經存在存檔裡的文字：規則只影響之後產生的輸出，已寫進存檔的「傑」不會自動改回「杰」。

## Decisions

1. **新能力 `rpg-output-traditional-chinese`，不併入既有規格。** 候選是 `rpg-turn-context`（系統指令與上下文）與 `llm-structured-calls`（結構化呼叫）。前者描述「送進模型的內容」，這份描述「模型輸出送達玩家之前的處理」；後者是客服與 RPG 共用的解析流程，簡轉繁只對 RPG 的三種用途生效。獨立成一個內聚的能力，之後要改套用範圍或保留清單都只動這一份。

2. **規格範圍是整個簡轉繁保證，不只「杰」。** 「杰」是基礎行為的一個例外，沒有「轉繁體」與「只在有簡體字時才轉」這兩條基礎需求，例外就沒有東西可以附著；而且基礎行為本來就缺規格。

3. **規格只寫可觀察的行為，不寫實作名稱。** 轉換用哪個套件與設定、簡繁共用字的清單、切開再轉的做法都屬實作，留在設計文件第 12 節；規格只寫：哪些輸出會轉、什麼情況轉、哪些字保留、什麼不被破壞。保留的字目前只有「杰」，寫在需求的文字裡，所以增加一個字要改這個需求。

4. **「杰」整類保留，而不是只在玩家文字出現過時才保留。** 另一個選項是只有該存檔的玩家文字出現過「杰」才保留（較精確），但要把存檔文字傳進轉換、改動大，且模型自己替 NPC 取名「杰」時也會被改掉；使用者在驗收時選擇「一律保留」。取捨寫進需求：簡體的「杰出」會留成「杰出」。

5. **英文不翻譯，只靠提示詞。** 翻譯需要多一次模型呼叫（每句多一次延遲與 token），而且驗收時用提示詞加強已經是使用者選的做法；偵測英文句後自動重生是之後可以評估的選項，頻率資料還不夠，所以規格只固定「伺服器端不翻譯、不擋下」。

## Risks / Trade-offs

- [規格與程式不一致] → 每個情境在 tasks 對照現有測試；沒有測試的（英文原樣送達）補測試；補完用破壞實作的方式確認測試真的會失敗。
- [簡體的「杰出」留成「杰出」] → 已寫進需求作為明文取捨；「杰」仍是可讀的異體字。
- [保留清單日後增加時漏改規格] → 清單只有一處實作、規格需求列出字，增加字的 change 必須同時有 MODIFIED 的 delta。

## Migration Plan

無：沒有程式、資料庫或設定變更，不需要部署。封存時 delta 同步成新的主規格 `rpg-output-traditional-chinese`。
