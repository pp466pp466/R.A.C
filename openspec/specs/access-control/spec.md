# access-control Specification

## Purpose
定義資料隔離與權限的基本規則：誰可以存取什麼由集中的政策決定，非擁有者一律得到「不存在」的回應，角色與會員等級各司其職，並提供可重複使用的測試方式與首位管理員的建立方法，供後續所有對話與後台功能沿用。

## Requirements

### Requirement: 權限判斷集中在政策物件
擁有者與管理員的判斷 SHALL 集中於單一政策物件，端點程式碼 SHALL NOT 自行寫權限判斷。政策 SHALL 至少回答：某人是否為資源擁有者、是否為管理員、是否可使用客服與其他 AI 功能（帳號為 `active`、已完成年齡確認且年齡不低於最低使用年齡，且在信箱驗證開啟時，信箱已驗證），以及目前的內容上限（未滿 18 歲固定為安全模式，成年者最高為 2）。年齡的所有判斷 SHALL 由生日於當下計算，且年齡規則 SHALL 只從集中的年齡設定讀取。

#### Scenario: 待驗證帳號使用客服
- **WHEN** 信箱驗證開啟，信箱尚未驗證的使用者詢問是否可使用客服
- **THEN** 政策判定為否

#### Scenario: 信箱驗證關閉時的啟用帳號
- **WHEN** 信箱驗證關閉，狀態為 `active`、驗證時間為空但已完成年齡確認的成年使用者詢問是否可使用客服
- **THEN** 政策判定為是

#### Scenario: 停權帳號
- **WHEN** 狀態為 `suspended` 的使用者詢問是否可使用客服
- **THEN** 政策判定為否

#### Scenario: 尚未確認年滿 18 歲
- **WHEN** 狀態為 `active`、信箱條件已滿足但尚未完成年齡確認的使用者詢問是否可使用客服
- **THEN** 政策判定為否

#### Scenario: 13 至 17 歲的使用者
- **WHEN** 已完成年齡確認、15 歲、其他條件齊全的使用者詢問是否可使用客服與內容上限
- **THEN** 可使用客服，內容上限為安全模式

#### Scenario: 年齡低於最低使用年齡
- **WHEN** 年齡設定的最低使用年齡高於使用者的年齡
- **THEN** 政策判定為否，且錯誤代碼與「尚未完成年齡確認」不同

#### Scenario: 檢查順序
- **WHEN** 帳號停權且尚未完成年齡確認
- **THEN** 回應的是帳號狀態的拒絕，不是引導補填年齡

### Requirement: 非擁有者一律得到 404
當使用者存取不屬於自己的資源時，系統 SHALL 回應 404 與「找不到」的訊息，SHALL NOT 回應 403 或任何會透露資源存在的差異；回應的狀態碼與內容 SHALL 與資源真的不存在時完全相同。授權 SHALL NOT 依賴識別碼的不可猜測性。

#### Scenario: 存取他人的資源
- **WHEN** 使用者 B 以使用者 A 之資源的對外識別碼發出讀取或寫入請求
- **THEN** 回應 404，內容與存取不存在的識別碼時相同

#### Scenario: 擁有者存取
- **WHEN** 使用者 A 存取自己的資源
- **THEN** 正常處理

### Requirement: 需要登入的端點
未登入者呼叫需要登入的 API 時，系統 SHALL 回應 401 與 JSON 錯誤；開啟需要登入的頁面時 SHALL 導向登入頁並保留安全的返回位置。已登入但狀態不允許的使用者 SHALL 得到對應的 403 說明。持有受限登入狀態（帳號為 `deletion_pending`）者 SHALL 視為「狀態不允許」，除非該端點或頁面明確允許受限狀態。

#### Scenario: 未登入呼叫 API
- **WHEN** 未登入者呼叫需要登入的 API
- **THEN** 回應 401 的 JSON 錯誤

#### Scenario: 未登入開啟受保護頁面
- **WHEN** 未登入者開啟需要登入的頁面
- **THEN** 導向登入頁，登入後返回原頁面

#### Scenario: 受限狀態呼叫 API
- **WHEN** 持有受限登入狀態者呼叫未明確允許受限狀態的 API
- **THEN** 回應 403 與代碼 `account_deletion_pending`，且不執行任何動作

#### Scenario: 受限狀態開啟其他頁面
- **WHEN** 持有受限登入狀態者開啟 `/account` 以外需要登入的頁面
- **THEN** 導向 `/account`

### Requirement: 角色與會員等級的語意
角色只有 `user` 與 `admin`，決定可存取的功能範圍；會員等級（`free`、`plus`、`vip`）SHALL 只影響額度，SHALL NOT 影響任何權限判斷。只有 `admin` 角色 SHALL 通過管理員判斷；使用者無法自行變更自己的角色或等級。

#### Scenario: 高等級不等於管理員
- **WHEN** 等級為 `vip` 的一般使用者詢問是否為管理員
- **THEN** 判定為否

#### Scenario: 一般使用者呼叫變更角色
- **WHEN** 一般使用者嘗試在任何 API 的輸入中帶入角色或等級欄位
- **THEN** 這些欄位被忽略，角色與等級不變

### Requirement: 權限測試框架
專案 SHALL 提供可重複使用的測試輔助，讓後續每個讀寫端點以「擁有者、非擁有者、不存在的識別碼、未登入」四種身分進行參數化檢查：非擁有者與不存在的識別碼必須得到相同的 404，未登入必須得到 401。框架本身 SHALL 附有自我驗證測試，證明它能抓出故意寫錯的端點。

#### Scenario: 框架抓得出漏洞
- **WHEN** 以一個故意不檢查擁有者的測試用端點執行框架
- **THEN** 框架判定失敗並指出是哪一種身分造成

#### Scenario: 正確的端點
- **WHEN** 以一個正確檢查擁有者的測試用端點執行框架
- **THEN** 框架判定通過

### Requirement: 以一次性指令建立首位管理員
系統 SHALL 提供由部署者執行的一次性命令列指令建立管理員帳號：密碼 SHALL 以不回顯的方式輸入（或由標準輸入讀取），SHALL NOT 作為命令列參數、不寫入日誌。建立的帳號角色為 `admin`、狀態為 `active`、信箱視為已驗證。信箱已存在時 SHALL 拒絕並說明，且不修改既有帳號。網頁註冊與任何 API SHALL NOT 能建立管理員或提升角色。

#### Scenario: 建立管理員
- **WHEN** 部署者執行指令並輸入信箱、顯示名稱與合規的密碼
- **THEN** 建立啟用狀態的管理員帳號，密碼以雜湊儲存，日誌沒有密碼

#### Scenario: 信箱已存在
- **WHEN** 以已被使用的信箱執行指令
- **THEN** 指令失敗並說明原因，既有帳號不變

#### Scenario: 網頁註冊不能取得管理員
- **WHEN** 註冊請求中帶有角色欄位
- **THEN** 該欄位被忽略，建立的帳號角色為 `user`

### Requirement: 會呼叫模型的端點先通過存取閘門
每個會呼叫模型或寫入客服對話的端點 SHALL 在做任何寫入與模型呼叫之前，先通過帳號、信箱與年齡閘門。閘門的結果 SHALL 只來自政策物件，端點不自行判斷。

#### Scenario: 閘門不通過
- **WHEN** 帳號尚未完成年齡確認而送出客服訊息
- **THEN** 回應 403，沒有任何資料被寫入、模型沒有被呼叫

#### Scenario: 信箱未驗證
- **WHEN** 信箱驗證開啟、使用者的信箱尚未驗證而送出訊息
- **THEN** 回應 403 與一般的「沒有權限」代碼，不引導補填年齡

### Requirement: 對話資料的存取一律帶擁有者條件
所有對話與訊息的讀寫 SHALL 以呼叫者的身分為條件；系統 SHALL NOT 提供只憑對話識別碼就能取得資料的存取路徑給 API 使用。管理員以一般端點存取他人的對話 SHALL 與一般使用者相同，得到 404。

#### Scenario: 管理員讀取他人對話
- **WHEN** 角色為管理員的使用者以一般客服端點讀取他人的對話
- **THEN** 回應 404，與不存在的對話相同

#### Scenario: 對話存取方法的簽名
- **WHEN** 檢查所有對話與訊息的資料存取方法
- **THEN** 每個提供給 API 使用的方法都要求擁有者參數

### Requirement: 管理員判斷只有一個入口，非管理員得到 404
所有後台功能 SHALL 先通過政策物件的管理員檢查；呼叫者不是「角色為 `admin` 且帳號為 `active`」時，檢查 SHALL 以與「資源不存在」完全相同的 404 拒絕，SHALL NOT 回應 403 或任何會透露後台存在的差異。每一次被拒絕 SHALL 記錄一筆只含內部使用者編號的事件。端點與其他 Service SHALL NOT 自行比對角色。

#### Scenario: 一般使用者
- **WHEN** 一般使用者通過後台的檢查
- **THEN** 以 404 拒絕，並記錄一筆含其內部編號的事件

#### Scenario: 管理員
- **WHEN** 狀態為 `active` 的管理員通過檢查
- **THEN** 允許

#### Scenario: 停權的管理員
- **WHEN** 狀態為 `suspended` 的管理員通過檢查
- **THEN** 以 404 拒絕

### Requirement: 管理員存取他人資料只走後台專用路徑並留下稽核
管理員讀取或改變他人的資料 SHALL 只能經由後台專用的 Service 與 Repository 方法，且每個這類操作 SHALL 寫入稽核紀錄；SHALL NOT 以放寬一般端點的擁有者條件來達成。一般使用者端點（例如 `/api/cs/*`）對管理員 SHALL 與對一般使用者相同。

#### Scenario: 一般端點不因角色放行
- **WHEN** 管理員以 `/api/cs/*` 讀取他人的對話
- **THEN** 回應 404

#### Scenario: 後台讀取留下稽核
- **WHEN** 管理員經由後台讀取他人的對話
- **THEN** 有一筆對應的稽核紀錄

### Requirement: 受限登入狀態預設拒絕
受限登入狀態 SHALL 預設拒絕：只有明確列入允許清單的端點能接受它，允許清單 SHALL 僅含查詢自己、撤銷刪除、登出與 `/account` 頁面。新增的需要登入的端點若沒有明確允許，SHALL 自動拒絕受限狀態，且 SHALL 有自動化測試掃描所有需要登入的端點來證明這一點。

#### Scenario: 允許清單以外的端點
- **WHEN** 測試以受限登入狀態逐一呼叫所有需要登入的 API
- **THEN** 允許清單以外的端點全部回應 403 與 `account_deletion_pending`

#### Scenario: 新增端點
- **WHEN** 開發者新增一個需要登入的端點而未列入允許清單
- **THEN** 該端點對受限狀態同樣回應 403
